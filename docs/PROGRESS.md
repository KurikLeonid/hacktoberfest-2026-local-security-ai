## M0: репо, инструменты, скелеты
- Склонирован пустой репозиторий, план положен в `docs/PLAN.md`.
- Установлены `ollama` (0.40) и `mitmproxy` через brew. В `backend` mitmproxy добавлен ещё и в uv-окружение (12.3), чтобы addon импортировал `core` с теми же зависимостями.
- `backend`: uv, Python 3.12+ (uv выбрал 3.13; системный 3.14 не используется).
- `frontend`: Vite + React 19 + TS + Tailwind 4, `/api` проксируется на :8000 в dev-режиме.
- **Отклонение**: gemma4:e4b весит 6,6 ГБ и качалась медленно (1–3 МБ/с), поэтому код M1–M4 писался параллельно с загрузкой.

## M1: политики, хранилище, классификатор
- `policies.yaml` и `core/policies.py`: валидация (категории, пороги, regex), hot reload по mtime, `allowed_categories(host)` с учётом поддоменов и `never_allowed`.
- `core/store.py`: SQLite в режиме WAL, общая для процесса прокси и процесса API. Таблицы `events` и `dataset`. `examples_for(category)` отдаёт решения security первыми, остальное случайно, отдельно по каждой метке.
- `core/classifier.py`: двухэтапный pipeline detect → policy filter → verify (few-shot по категории) → score. JSON-схема передаётся в `format` Ollama (structured output), `temperature 0`, `think: false`. Общий таймаут 15 с. Любая ошибка поднимает `ClassifierError`, а это BLOCK.
- Вызовы Ollama идут с `trust_env=False`, иначе при включённом системном прокси httpx отправил бы их в собственный прокси.
- Проверено: pipeline на заглушке модели (фильтр по домену, верификация, подсветка offset'ов). Проверка на живой Gemma: см. M5.

## M2: прокси
- `proxy/guard.py`: async-хук `request`. ALLOW пропускает. BLOCK отдаёт 403 с JSON-ошибкой. REVIEW держит запрос: каждые 0,5 с опрашивает SQLite до решения или до таймаута, при таймауте `expired` и 403.
- TLS расшифровывается только для `inspect_domains`: при старте ставится `allow_hosts`, остальное passthrough.
- `proxy/adapters.py`: ChatGPT (`/backend-api/(f/)conversation`, `messages[].content.parts` роли user), Claude (`…/chat_conversations/*/completion`, `prompt` и `attachments[].extracted_content`). Generic-адаптер (JSON-строки, form, text) работает только для inspect-доменов без собственного адаптера, поэтому телеметрия ChatGPT/Claude не уходит в модель.
- `core/notify.py`: уведомление macOS через `terminal-notifier` (клик открывает админку), если он установлен, иначе через `osascript`. Фрагменты в уведомлении маскируются.
- `scripts/dlp-on.sh` / `dlp-off.sh` (`networksetup` на сервисе активного интерфейса) и `run.sh` (Ollama, API, прокси; trap → dlp-off).
- Проверено: `curl -x 127.0.0.1:8080` на `chatgpt.com/backend-api/f/conversation` без модели даёт 403 fail-closed и событие в SSE. `example.com` проходит насквозь (200).

## M4.5: временная облачная модель (вне плана)
**Почему:** gemma4:e4b (6,6 ГБ) качалась 2–3 МБ/с. Команда решила не ждать загрузки и проверить остальное на Gemini, а потом заменить на Gemma.
- Провайдер переключается переменной `DLP_LLM_PROVIDER=gemini|ollama` в `backend/.env`. Файл в .gitignore, ключ в репозиторий не попадает. По умолчанию `ollama`: продукт остаётся локальным.
- Пока включён облачный провайдер, в шапке админки висит красная плашка «облачная модель: только для разработки». В этом режиме данные уходят в Google, демо так показывать нельзя.
- Модель: `gemini-3.8-flash` отвечала «high demand» или зависала на 40 с, у `gemini-3.5-flash` free-tier лимит 5 запросов в минуту (одна проверка = 2 запроса). Работаем на `gemini-3.5-flash-lite`: 1–3 с на проверку, иногда до 11 с.

### Живая проверка классификатора (gemini-3.5-flash-lite)
| Текст | Домен | Результат |
|---|---|---|
| Вопрос про linked list | chatgpt.com | ALLOW 0.0 |
| AWS-ключи | claude.ai | BLOCK 0.95–1.0 (credentials запрещены везде) |
| Письмо клиенту: имя, email, телефон, карта | chatgpt.com | BLOCK 1.0 (pii + financial) |
| Внутренняя функция биллинга | claude.ai | ALLOW (source_code разрешён) |
| Та же функция | chatgpt.com | REVIEW 0.8 (до калибровки был BLOCK 0.95) |
| Q3 roadmap + клиент Acme | chatgpt.com | BLOCK 0.9 (internal_docs 0.75, customer_data 0.9) |
| `os.getenv('OPENAI_API_KEY')` + `your-api-key-here` | chatgpt.com | ALLOW (плейсхолдер распознан) |

- **Отклонение (промпт):** без калибровки верификатор ставил коду 0.95, и всё сразу шло в BLOCK. В промпт верификатора добавлена шкала: 0.9+ только для однозначного вреда (ключи, карты, ID, контакты человека), 0.5–0.85 для того, что требует человека (код, внутренние документы).

### End-to-end через прокси (`curl -x`, ChatGPT/Claude-формат тела)
- REVIEW → Approve: запрос держится, после Approve уходит на chatgpt.com. В датасет добавляется 1 строка `not_sensitive / security`.
- **Обратная связь подтверждена:** повторная отправка того же кода после Approve даёт ALLOW (верификатор 0.05 на примере от security).
- REVIEW → Reject: клиент получает 403 «rejected by security», в датасет добавляется строка `sensitive / security`.
- BLOCK (ключи в claude.ai): 403 за ~5 с, сообщение с маской `AKIA••••••••`, уведомление macOS.
- Fail-closed без модели: 403 (проверено в M2).
- REVIEW без решения: через 60 с статус `expired`, клиент получает 403 «no security decision in time» (запрос висел 65 с).

## M5: живой тест в Chrome под системным прокси (модель пока Gemini)
- `scripts/run.sh` включает системный прокси для Wi-Fi. Обычные сайты проходят насквозь без расшифровки.
- **Адаптер ChatGPT на реальном трафике работает:** браузер шлёт `POST /backend-api/f/conversation`, промпт извлекается.
- Обычный вопрос → ALLOW, ответ пришёл. AWS-ключи в ChatGPT → BLOCK 0.95.
- Функция биллинга → ALLOW: раньше security одобрил её через `curl`, и модель опирается на этот пример (обратная связь работает, но в сценарии демо это нужно учитывать).
- **Отклонение (политика):** порог BLOCK поднят с 0.85 до 0.9, чтобы совпадать со шкалой верификатора (0.5–0.85 — «нужен человек»). Модель поставила новому коду ровно 0.85, и он ушёл в BLOCK.
- **Наблюдение:** уверенность, которую модель сообщает о себе, «плавает» на ±0.05 на одном и том же тексте (0.85 → 0.9), поэтому код иногда идёт в BLOCK вместо REVIEW. Команда решила оставить как есть, без потолка REVIEW для отдельных категорий.
- **UI:** в карточке события, в журнале и в «Проверить текст» теперь есть шкала: уверенность модели и пороги REVIEW/BLOCK. Раньше был виден только score, и его путали с порогом.
- **Адаптер Claude на реальном трафике работает:** `POST /api/organizations/<uuid>/chat_conversations/<uuid>/completion`, промпт извлекается.
- Whitelist работает на живом трафике: тот же код из pricing engine в claude.ai → ALLOW (модель нашла `source_code`, но он разрешён для домена), в chatgpt.com → BLOCK 0.9. AWS-ключи в claude.ai → BLOCK 1.0 (credentials запрещены везде).
- Задержка проверки на Gemini flash-lite в браузере: 4,7–9 с.

## Этап 2: сложные eval-тесты, GDPR special_pii, нецелевые запросы
План этапа согласован через grilling (вопросы Q1–Q15). Суть: eval-набор для сравнения моделей + отчёт + промпты для демо.
- **Новая категория `special_pii`** (GDPR ст. 9/10: здоровье, вес, беременность, биометрия, религия, происхождение, ориентация, профсоюз, политика, судимости), запрещена везде, как `credentials`. Описание включает непрямую идентификацию («единственный бухгалтер в Берлине…»). В админке выделена отдельным цветом.
- **Детектор** учитывает обфускацию: словами, через дефисы, «dot/at», транслит, таблицы, данные внутри длинного текста. Публичные факты, исторические личности, вымышленные персонажи и известные тестовые карты (4242…) он игнорирует.
- **Шкала верификатора**: рабочий email вида name.surname@company и любые special_pii про идентифицируемого человека дают 0.9+. `company_domains` в политику не добавляли (решение команды).
- **Нецелевые запросы**: тот же вызов детектора возвращает `purpose {work, topic, confidence}`. Граница задаётся в `policies.yaml` → `purpose`. На всех доменах действие ALLOW + статистика: метка «нецелевой: тема» в журнале и карточке, панель над журналом (доля за 24 ч по доменам, топ тем). `GET /api/stats`. Колонка `events.purpose` добавляется миграцией при старте.
- **Eval** (`backend/eval/`): 42 кейса (65 проверок: часть кейсов идёт на оба домена), EN/RU. `run.py`: `--provider gemini|ollama --model --runs --examples hf|all --rpm --timeout --only`. Ретраи на 429/503, троттлинг под free tier. Результаты пишутся в `eval/results/*.json`, отчёт в `docs/EVAL.md` (метрики: утечки, ложные блоки, мягкие ошибки, ошибки модели, полнота категорий, точность цели, p50/p95, нестабильность).
- **Изоляция eval**: few-shot только из HF-примеров (`--examples hf`), события и датасет не пишутся.
- **Первый полный прогон на Gemini flash-lite (до исправления):** 63/65 (97%), утечек 2, ложных блоков 0, special_pii 20/20, точность цели 100%, p50 4.4 с / p95 10.2 с. Обе утечки — `pii-work-email`: детектор нашёл `leonid.kurik@semrush.com`, а верификатор снизил оценку до 0.1–0.2 как «подпись самого автора».
- **Исправление (промпт верификатора):** собственные имя, email и телефон автора в подписи — тоже персональные данные сотрудника, снижать оценку из-за этого нельзя. Повтор `pii-work-email` и соседних негативов ×3: 15/15, email → BLOCK стабильно, негативы и письмо в HR про отпуск остаются ALLOW.
- **Полный прогон после исправления (Gemini flash-lite):** 65/65 (100%), утечек 0, ложных блоков 0, мягких 0, полнота категорий 90%, цель 100%, p50 5.3 с / p95 8.6 с. Отчёт: [EVAL.md](EVAL.md).

## Этап 2: переход на Gemma 4
- Gemini заменён на локальную Gemma: `DLP_LLM_PROVIDER=ollama` в `backend/.env`.
- **Отклонение:** на Mac тег `gemma4:e4b` ставит MLX-сборку, а она не поддерживает structured output (`501 structured output is unavailable`, в том числе `format: "json"`). Добавлен запасной путь: схема передаётся текстом в промпте, JSON извлекается из ответа. Режим определяется один раз за процесс.
- **Проблема скорости:** MLX-сборка занимает в памяти 17 ГБ на Mac с 16 ГБ, своп заполнен на 9,4 из 10 ГБ. С продовым таймаутом 15 с около трети проверок упирались в таймаут и получали BLOCK (fail-closed), поэтому этот прогон остановлен.
- **Качество Gemma** (прогон с таймаутом 120 с, чтобы отделить качество от скорости): 64/65 (98%), утечка 1, ложных блоков 0, полнота категорий 94% (у Gemini 90%), цель 100%, p50 11 с / p95 22 с (со свопом).
- Утечка: план M&A с кодовым названием для ChatGPT получил ALLOW, детектор ничего не нашёл. В описание `internal_docs` добавлены неанонсированные сделки, M&A, кодовые названия и пометка «confidential». После этого ×3: chatgpt → BLOCK 3/3. В claude.ai теперь REVIEW 3/3: кодовое название разрешено как internal_docs, но сумма `$20M` распознаётся как `financial`, а эта категория для claude.ai не разрешена. Поведение логичное, ожидание в кейсе можно пересмотреть.
- **Следующий шаг (не сделан):** квантованная `gemma4:e4b-it-q4_K_M` (5,5 ГБ, llama.cpp, structured output) должна поместиться в память без свопа. Загрузку начали и остановили по решению команды на 5%.
- Логотип v2 (`docs/logo-v2.svg`) встроен в шапку админки и в иконку вкладки: охранник не даёт сотруднику с бейджем и шапкой-маскотом нажать ENTER.

## Этап 2: оптимизация задержек на текущей Gemma (без новой загрузки)
- Причина 17 ГБ: в E4B на самом деле 8.1B параметров (часть — эмбеддинги для каждого слоя). Сборка `nvfp4` на M1 без FP4, вероятно, распаковывается в 16 бит. Заменить модель не успеваем, поэтому ускоряем обработку каждого запроса.
- Верификатор проверяет не больше 4 находок (не больше 2 на категорию). Остальные находки получают вердикт своей категории, потому что score всё равно берётся по максимуму. Объяснения не длиннее 12 слов, `num_predict 512`, 2 примера на метку вместо 3, контекст примеров короче. Прокси прогревает модель при старте.
- Замеры (detect + verify): обычный вопрос 3.6 → 1.5 с, непрямая идентификация 6.1 → 5.2 с, CSV с сотрудниками 22.6 → 13.1 с. После `ollama stop` своп освободился; заметная часть прежних задержек была из-за нехватки памяти.
- `model_timeout_s` поднят с 15 до 25 с: тяжёлые тексты укладываются в 12–14 с с запасом.
- Проверка ×2 кейса: CSV сотрудников → BLOCK 0.95 за 12.8 / 13.7 с, Stripe 4242 → ALLOW за 1.0 с. Полный eval после оптимизации не запускали (решение команды).
- Gemini API: добавлен разбор ответов Gemma с thinking-частями и повтор без JSON-схемы при 500. Обе Gemma 4 в API (26B-A4B, 31B) доступны по ключу, но это облако; 31B проверили только на нескольких кейсах.
